> *Програмно-апаратний комплекс повітряної оптико-електронної розвідки та аналізу даних дистанційного зондування Землі*

## 1. Загальна візія та архітектурні інваріанти системи

### 1.1. Призначення та предметна область
Програмний комплекс призначений для автоматизованого високоточного виявлення, класифікації та локалізації малорозмірних об'єктів (наземної та надводної техніки, літальних апаратів, промислових і фортифікаційних споруд за таксономією DOTA 1.5 / VisDrone) на аерофотознімках надвисокої роздільної здатності (4K, 8K та панорами до $13000 \times 13000\text{ px}$ і більше).

Комплекс спроєктовано для функціонування в умовах **жорсткого дефіциту обчислювальних ресурсів**:
- Локальні автоматизовані робочі місця (АРМ) оператора з дискретними GPU споживчого класу (1–4 ГБ VRAM).
- Мобільні та бортові обчислювальні модулі безпосередньо на носіях (NVIDIA Jetson Orin/Xavier, компактні x86/ARM платформи).
- Робочі станції без виділеного апаратного прискорювача NVIDIA (із забезпеченням прозорого апаратного або процесорного резервування через DirectML або OpenVINO/CPU).

Традиційні підходи нейромережевої детекції (безпосередня подача 8K кадру в згорткову або трансформерну мережу) призводять до фатальної помилки `CUDA Out of Memory` через квадратичне зростання обсягу тензорів проміжних карт ознак ($O(W \cdot H)$), або до катастрофічної втрати інформації при простому глобальному стисненні панорами до стандартного розміру 640 px (малорозмірний об'єкт площею $20 \times 20\text{ px}$ стискається у субпіксельну пляму менше 1 px і стає математично невиразним для рецептивних полів детектора). Дана система розв'язує цю проблему за допомогою конвеєра аналітичної декомпозиції простору на базі динамічного тайлінгу з наступним об'єднанням детекцій без деградації роздільної здатності.

### 1.2. Фундаментальні архітектурні інваріанти системи

Уся архітектура системи спирається на п'ять ключових інваріантів, суворе дотримання яких гарантується на рівні ядра C++, графічного диспетчера та модульних тестів:

```

+---------------------------------+---------------------------------+-------------------------------+
|  1. Hardware-Aware Dynamic      |  2. In-Memory Zero-Copy         |  3. Zero PCIe Readback        |
|     Tiling                      |     Slicing                     |                               |
|  - T_calc(VRAM, H)              |  - Відсутність дискового I/O    |  - Односпрямований транзит    |
|  - Квантування {320,416,512,640}|  - CUDA kernel extract_tile_gpu |  - Зворотний трафік O(N)      |
|  - Адаптивне вікно 736 px       |  - Паралельний RGB normalizer   |  - Заощадження >99.97% PCIe   |
+---------------------------------+---------------------------------+-------------------------------+
|  4. Metadata-Driven             |  5. DRY-ядро (C++20 & pybind11)                                 |
|     Non-Destructive UI          |                                                                 |

|  - Миттєва фільтрація без I/O   |  - Відсутність дублювання логіки у C++ та Python               |
+---------------------------------+-----------------------------------------------------------------+
```

#### I. Hardware-Aware Dynamic Tiling (Адаптивна геометрія декомпозиції)
Параметри просторової сітки розбиття не є захардкодженними константами. Вони розраховуються аналітично у функціях [`calculate_tiling_params()`](file:///workspaces/MD/src/tiling_math.cpp#L32) ядра C++ як функція висоти зйомки польоту $H$ (метрів) та фізичного ліміту доступної відеопам'яті $VRAM_{MB}$:
$$T_{\text{calc}} = \frac{VRAM_{MB}}{4} + H \cdot 10$$
Отримане теоретичне значення $T_{\text{calc}}$ квантується у найбільшу підтримувану сітку моделей $M_{\text{selected}} \in \{320, 416, 512, 640\}$. 
Для надвеликих панорам ($\max(W, H) \ge 5000\text{ px}$) застосовується спеціальне адаптивне розширене вікно нарізки $T_{\text{slice}} = 736\text{ px}$, що ресайзиться до базової нейромережі 640 px, зменшуючи сумарну кількість фрагментів на 22–25% без втрати дрібних деталей.
Коефіцієнт швів динамічно обмежується діапазоном $O_{\text{lap}} \in [0.15, 0.20]$:
$$O_{\text{lap}} = \text{clamp}\left(0.15 + \frac{H}{3000}, 0.15, 0.20\right)$$
Для середніх кадрів ($\max(W, H) \le 1500\text{ px}$) діє евристика Edge Safeguard, яка примусово обмежує сітку до розміру не більше $3 \times 3$ і максимум 6 плиток, усуваючи паразитне надлишкове дроблення та падіння FPS.

#### II. In-Memory Zero-Copy Slicing (Внутрішньопам'ятна фрагментація без дискового I/O)
Система повністю виключає створення будь-яких проміжних файлів на накопичувачі (`.jpg`, `.png`, `.bmp`) під час нарізки плиток.
- **У конвеєрі GPU (C++/CUDA):** кадр завантажується безпосередньо у відеопам'ять. Спеціалізоване ядро CUDA [`extract_tile_kernel`](file:///workspaces/MD/src/cuda_slicer.cu#L12) паралельно вибирає потрібну ділянку пам'яті, виконує апаратну білінійну інтерполяцію, перетворює колірний порядок з чередованого BGR `uint8` у планарний RGB `float32` [1, 3, Target, Target], нормує діапазон $[0, 255] \to [0.0, 1.0]$ та записує результат у попередньо виділений тензор VRAM.
- **У конвеєрі CPU/Host (Python/NumPy):** субтензори формуються за допомогою безнавантажувальних зрізів масивів NumPy (`view`), не створюючи дублікатів повнорозмірного кадру в оперативній пам'яті.

#### III. Zero PCIe Readback (Односпрямований транзит даних через шину PCIe)
Обмін даними між процесором (Host) та прискорювачем (Device) організовано як строго односпрямований потік:
1. Повнорозмірний кадр завантажується в GPU один раз.
2. Фрагментація, прямий прохід моделей та первинна фільтрація виконуються повністю у просторі VRAM.
3. Через шину PCIe у зворотний бік (Device $\to$ Host) передаються **виключно легковагові чисельні вектори детекцій** розмірністю $O(N)$, де $N$ — кількість знайдених цілей (структури `x, y, w, h, conf, class_id`), обсяг яких становить лічені кілобайти.
4. Повний растр $8\text{K}$ кадру (понад 100 МБ у пам'яті) **ніколи не зчитується назад із GPU**. У режимі пакетного тріажу (`BatchTriageWorker`) збереження позитивних кадрів на диск здійснюється прямою реплікацією з диска на диск через системний виклик `shutil.copy2` із записом супутнього JSON-файлу метаданих, що скорочує зворотний трафік шини PCIe на **99.97%**.

#### IV. Metadata-Driven Non-Destructive UI (Метадані без пошкодження растру)
Графічний інтерфейс користувача побудовано за концепцією недеструктивного відображення:
- Робоча сцена [`QGraphicsScene`](file:///workspaces/MD/gui/canvas_viewer.py#L137) строго розділена на ізольовані Z-шари.
- **Шар $Z = 0.0$:** містить чистий оригінальний піксельний растр [`QGraphicsPixmapItem`](file:///workspaces/MD/gui/canvas_viewer.py#L291). Растрові пікселі в пам'яті є недоторканними: на них ніколи не малюються лінії графічним редактором OpenCV (`cv2.rectangle`) чи QPainter.
- **Шар $Z \ge 10.0$:** містить векторні примітиви (`QGraphicsRectItem`, `QGraphicsSimpleTextItem`). Межі прямокутників відмальовуються косметичним пеном (`QPen.setCosmetic(True)`), який зберігає постійну фізичну товщину в 2 px на екрані при будь-яких коефіцієнтах масштабування від оглядового 2% до піксельного 3200%.
- Зміна порогового значення впевненості (Confidence Slider) або перемикання видимості класів (Class Visibility Filter) виконується миттєво ($< 1\text{ мс}$) як локальне перемикання прапорця видимості `item.setVisible()`, не вимагаючи повторного читання файлу чи повторного рендерингу растру.

#### V. DRY-принцип (Спільне ядро C++20 та pybind11)
Щоб уникнути розсинхронізації логіки декомпозиції між навчанням нейромережі та бойовим виконанням, єдине скомпільоване ядро C++20 [`libtiling_core`](file:///workspaces/MD/CMakeLists.txt#L52) обгорнуто у модуль розширення Python [`pytiling_core`](file:///workspaces/MD/bindings/bindings.cpp#L35).
Скрипт підготовки навчальних вибірок [`train_pipeline/dataset_slicer.py`](file:///workspaces/MD/train_pipeline/dataset_slicer.py#L31) викликає **ту саму C++ функцію** `calculate_tiling_params()`, що й бойовий рантайм `main_pipeline` та GUI-воркер `InferenceWorker`. Це гарантує 100% геометричну відповідність тайлів під час інференсу тому, на чому нейромережа навчалася.

### 2.1. Модуль розрахунку динамічної сітки: `tiling_math`
- **Шляхи до файлів:** [`include/tiling_math.hpp`](file:///workspaces/MD/include/tiling_math.hpp), [`src/tiling_math.cpp`](file:///workspaces/MD/src/tiling_math.cpp).
- **Зона відповідальності:** Чистий аналітичний розрахунок координат вікон декомпозиції кадру без взаємодії з диском чи GPU.
- **Ключові структури та функції:**
  * `struct Rect { int x, y, w, h; }`: Опис прямокутного регіону тайла в піксельних координатах вихідного зображення.
  * `struct TilingConfig`: Контейнер результатів планування сітки, що містить `tile_size`, `overlap`, `grid_cols`, `grid_rows` та `std::vector<Rect> tiles`.
  * `TilingConfig calculate_tiling_params(int image_width, int image_height, float altitude, size_t vram_available_mb)`: Головна математична функція планувальника.
- **Технічні особливості реалізації:**
  * *Edge Alignment:* Рівномірний розподіл кроку між плитками без «звалювання» швів на крайніх зонах:
    $$y_r = \text{round}\left(\frac{r \cdot (H - T_{\text{size}})}{N_{\text{rows}} - 1}\right)$$
  * *Scale Protection:* Автоматичне розширення вікна до 736 px для панорам розміром $\ge 5000\text{ px}$.
  * *Overtiling Guard:* Запобігання виродженню сітки на кадрах до 1500 px.
- **Вхідні дані:** Розміри кадру ($W, H$), висота зйомки в метрах ($H_{\text{alt}}$), доступний обсяг VRAM (МБ).
- **Вихідні дані:** Структура `TilingConfig` з повним переліком прямокутників сітки.

### 2.2. Модуль GPU-фрагментації: `cuda_slicer`
- **Шляхи до файлів:** [`include/cuda_slicer.cuh`](file:///workspaces/MD/include/cuda_slicer.cuh), [`src/cuda_slicer.cu`](file:///workspaces/MD/src/cuda_slicer.cu).
- **Зона відповідальності:** Вирізання фрагментів зображення із загального буфера пам'яті VRAM, просторове масштабування (resize) та канальна нормалізація.
- **Ключові компоненти:**
  * `__global__ void extract_tile_kernel(...)`: Обчислювальне ядро CUDA. Конфігурація ниток: блок $32 \times 8$ (256 потоків), де кожна нитка обчислює вихідний піксель $(o_x, o_y)$ одночасно для 3 колірних каналів.
  * `cudaError_t extract_tile_gpu(...)`: Хост-обгортка виклику ядра.
- **Технічні особливості реалізації:**
  * *Bilinear Filtering on Device:* Ручний розрахунок вагових коефіцієнтів білінійної інтерполяції ($\alpha, \beta, w_{00}, w_{10}, w_{01}, w_{11}$) на регістрах GPU без залучення важких бібліотек.
  * *Interleaved BGR to Planar RGB:* Одночасна зміна формату упаковки з чередованого BGR (формат OpenCV/V4L2) у планарний RGB NCHW `[3][Target][Target]` з діленням на 255.0f.
- **Вхідні дані:** Покажчик `d_src_img` у VRAM (`uint8_t`), розміри кадру, координати `TileRect`, цільовий розмір $M$.
- **Вихідні дані:** Виділений буфер `d_dst_tensor` у VRAM (`float32`).

### 2.3. Модуль постобробки та шовної фільтрації: `postprocess`
- **Шляхи до файлів:** [`include/postprocess.hpp`](file:///workspaces/MD/include/postprocess.hpp), [`src/postprocess.cpp`](file:///workspaces/MD/src/postprocess.cpp).
- **Зона відповідальності:** Ремапінг координат цілей у глобальний простір кадру, придушення дублікатів на стиках тайлів, ліквідація фрагментарних рамок та серіалізація в JSON.
- **Ключові структури та функції:**
  * `struct GlobalDetection`: Об'єкт у системі координат оригінального зображення (`x, y, w, h, conf, class_id, tile_id`).
  * `remap_offsets(...)`: Перерахунок локальних координат детектора в координати кадру:
    $$x_{\text{global}} = X_0 + x_{\text{local}} \cdot \left(\frac{W_t}{M_{\text{selected}}}\right)$$
  * `calculate_diou(...)`: Розрахунок Distance-IoU:
    $$\text{DIoU} = \text{IoU} - \frac{\rho^2(b, b^{gt})}{c^2}$$
  * `calculate_containment(...)`: Розрахунок критерію Intersection over Smaller (IoS):
    $$\text{IoS} = \frac{|A \cap B|}{\min(|A|, |B|)}$$
  * `cluster_diou_nms(...)`: Кластеризація та злиття рамок на швах тайлів.
  * `to_json_string(...)`: Формування компактного JSON-рядка для відправки клієнту/GUI.
- **Технічні особливості реалізації:**
  * *Sweep-and-Prune Optimization:* Сортування меж-кандидатів за координатою $X$ для швидкого відсікання пар, перетин яких неможливий ($x_j \ge x_i + w_i$), що знижує асимптотику NMS з $O(N^2)$ до $O(N \log N)$.
  * *Containment / IoS Suppression:* Якщо фрагмент об'єкта перетинає межу на $\ge 88\%$ меншої площі і менша площа становить $\le 80\%$ більшої, рамка-фрагмент поглинається повнорозмірною рамкою з максимальним збереженням впевненості $\max(\text{conf}_i, \text{conf}_j)$.
  * *Confidence-Weighted Coordinate Averaging:* Злиття еквівалентних рамок одного класу на шві:
    $$\bar{x} = \frac{\sum \text{conf}_i \cdot x_i}{\sum \text{conf}_i}, \quad \bar{y} = \frac{\sum \text{conf}_i \cdot y_i}{\sum \text{conf}_i}, \quad \text{conf}_{\text{merged}} = \max_i(\text{conf}_i)$$
- **Вхідні дані:** Вектор локальних детекцій `std::vector<Detection>`, координати тайла, пороги DIoU/впевненості.
- **Вихідні дані:** Вектор валідованих глобальних детекцій `std::vector<GlobalDetection>`, JSON-строка.

### 2.4. Модуль нативного інференсу TensorRT: `trt_detector`
- **Шляхи до файлів:** [`include/trt_detector.hpp`](file:///workspaces/MD/include/trt_detector.hpp), [`src/trt_detector.cpp`](file:///workspaces/MD/src/trt_detector.cpp).
- **Зона відповідальності:** Прямий прохід компільованих планів TensorRT (`.engine`) безпосередньо з C++ через NVIDIA TensorRT C++ API.
- **Ключові класи:**
  * `class TRTDetector`: Клас-обгортка над сесією виконання. Використовує патерн *PImpl (Pointer to Implementation)* для ізоляції заголовків `NvInfer.h` від зовнішніх модулів.
  * `struct TRTDeleter`: RAII-деструктор для коректного вивільнення об'єктів `nvinfer1::IRuntime`, `ICudaEngine`, `IExecutionContext` відповідно до сучасного стандарту TensorRT 8/10.
- **Технічні особливості реалізації:**
  * Повна відсутність операцій копіювання Device $\leftrightarrow$ Host під час інференсу: метод `infer(const float* d_input_tensor)` приймає безпосередній VRAM-покажчик і виділяє пам'ять під вихідні детекції у VRAM.
  * Використання асинхронного виконання через `enqueueV3` / `execute_async_v3` у виділеному потоці `cudaStream_t`.

### Детальний опис стадій конвеєра:

#### Етап I. Завантаження та препроцесинг (I/O & Image Ingestion)
1. Кадр зчитується з носія інформації у фоновому потоці.
2. Підтримуються формати RAW/TIFF/JPEG/PNG/BMP з глибиною кольору 8 біт на канал.
3. Растровий масив декодується без блокування основного GUI-потоку застосунку.

#### Етап II. Геометричне планування декомпозиції (Grid Calculation)
1. Модуль `tiling_math` за мілісекунду обчислює оптимальну геометрію сітки відповідно до поточного ліміту пам'яті та висоти зйомки.
2. Визначається базова резолюція моделі $M \in \{320, 416, 512, 640\}$.
3. Застосовуються алгоритми запобігання надлишковому тайлінгу (Edge Safeguard) та розширення вікна до 736 px для панорам.

#### Етап III. Внутрішньопам'ятна фрагментація (In-Memory Slicing)
1. Без створення тимчасових файлів фрагменти формуються паралельно безпосередньо у пам'яті.
2. Векторизується білінійна інтерполяція розміру плитки до вхідного шару обраної нейромережі.
3. Здійснюється транспонування вимірів із HWC (висота, ширина, канали) у NCHW (батч, канали, висота, ширина) та нормування значень у діапазон $[0.0, 1.0]$.

#### Етап IV. Нейромережевий інференс (Hardware-Accelerated Inference)
1. Пакет або послідовність підготовлених тензорів передається у скомпільовану сесію виконання.
2. У разі наявності NVIDIA GPU активується TensorRT C++ або `CUDAExecutionProvider`.
3. На платформі Windows за відсутності CUDA автоматично запускається `DmlExecutionProvider` (DirectML), що підтримує будь-які GPU (NVIDIA, AMD Radeon, Intel Arc).
4. За повної відсутності апаратних прискорювачів інференс детерміновано виконується через `CPUExecutionProvider`.
5. Після завершення проходу проміжні тензори вхідних фрагментів негайно видаляються з відеопам'яті, гарантуючи відсутність витоків пам'яті.

#### Етап V. Просторова постобробка та шовна фільтрація (Post-Processing)
1. **Host-Device Offset Mapping:** Локальні координати детекцій на кожному тайлі повертаються у простір вихідного зображення:
   $$x_{\text{global}} = X_0 + x_{\text{local}} \cdot \left(\frac{W_t}{M}\right), \quad y_{\text{global}} = Y_0 + y_{\text{local}} \cdot \left(\frac{H_t}{M}\right)$$
2. **Containment / IoS Suppression:** Перевіряються пари перекриття на швах. Якщо фрагмент об'єкта, розрізаного лінією тайлінгу, потрапив на сусідню плитку як зменшена хибна ціль ($\text{IoS} \ge 0.88$, площа $\le 80\%$), він безповоротно придушується.
3. **Cluster-DIoU-NMS:** Повнорозмірні дублікати одного об'єкта на швах тайлів кластеризуються графовим алгоритмом пошуку компонент зв'язності (BFS) та зливаються в єдиний Bounding Box зі зваженими координатами та максимальною впевненістю.

#### Етап VI. Візуалізація та експорт результатів (Output & UX)
- **Режим Stream View (Робота оператора в GUI):** Векторні примітиви додаються на шари $Z \ge 10$ компонента `CanvasViewer`. Оператор може миттєво змінювати масштаб від повного кадру до окремої цілі без перевантаження растру.
- **Режим Batch Triage (Пакетне сортування масивів аерознімків):** Якщо на кадрі виявлено цілі, файл оригіналу реплікується прямо з диска на диск (`shutil.copy2`) у папку призначення, а поруч записується супутній JSON-кеш із точними координатами цілей, відсотками впевненості та класами. Порожні кадри ігноруються.

## 4. Матриця технологій та залежностей за етапами пайплайну

| Крок конвеєра / Підсистема | Основна мова / Стандарт | Використані бібліотеки та фреймворки | Архітектурне обґрунтування вибору |
| :--- | :--- | :--- | :--- |
| **I. Image Ingestion & I/O** | C++20 / Python 3.10+ | OpenCV (`cv2`), `shutil`, `Pathlib` | Висока швидкість нативного декодування популярних форматів аерозйомки; пряма реплікація disk-to-disk без проміжного буфера RAM. |

| **III. In-Memory Slicing** | CUDA C++ / Python 3.10+ | NVIDIA CUDA Toolkit (nvcc, CUDA Runtime API), NumPy Strides | Паралельна білінійна інтерполяція та зміна розмірності безпосередньо у відеопам'яті GPU, усунення перевантаження системної шини. |

## 5. Інфраструктура збірки, тестування та дистрибуції

### 5.1. Система збірки (CMake 3.20+)
Проєкт використовує сучасний декларативний `CMakeLists.txt`, налаштований на роботу в гібридному режимі (C++20 та CUDA):
- **Прапорці компіляції:** `CMAKE_CXX_STANDARD 20`, `CMAKE_POSITION_INDEPENDENT_CODE ON`.
- **Керування рантаймом CUDA:** Встановлено `set(CMAKE_CUDA_RUNTIME_LIBRARY Shared)` для запобігання конфліктам статичної лінковки `libcudart` між різними версіями компіляторів.
- **Модульність та таргети збірки:**
  * `tiling_math` (STATIC): Базова бібліотека математики розбиття.
  * `postprocess` (STATIC): Бібліотека зміщення координат та NMS.
  * `cuda_slicer` (STATIC): Опціональний модуль ядра CUDA (активується за наявності `nvcc`).
  * `trt_detector` (STATIC): Опціональний модуль TensorRT (активується за наявності `NvInfer.h`).
  * `main_pipeline` (EXECUTABLE): Автономний нативний консольний пайплайн.
  * `pytiling_core` (MODULE): Динамічна бібліотека розширення Python, зібрана за допомогою `pybind11`.

### 5.3. Комплекс верифікації та тестування
Система тестування дворівнева:
1. **Нативний рівень (CTest):**
   * `test_tiling_math`: Перевірка формул $T_{\text{calc}}$, крайового вирівнювання та стабільності розмірів плиток.
   * `test_postprocess`: Перевірка DIoU, IoS Containment та злиття рамок на швах.
   * `test_cuda_slicer`: Перевірка коректності білінійної інтерполяції CUDA-ядра.
   * `test_trt_detector` & `test_main_pipeline`: Інтеграційні тести нативного конвеєра.
2. **Інтеграційний рівень (PyTest & `validate_system.py`):**
   * Повний тестовий набір (113 тестів у директорії `tests/`) покриває всі сценарії: перемикання станів аналізу, відсутність дублювання логіки, коректність палітри інтерфейсу, завантаження моделей та фонові потоки.
   * Автономний скрипт [`validate_system.py`](file:///workspaces/MD/validate_system.py) виконує 5-етапний аудит архітектурних інваріантів:
     1. *DRY Binding Integrity:* Імпорт `pytiling_core` та валідація 8K сітки (13 колонок $\times$ 8 рядків, 104 плитки).
     2. *Offset Mapping Geometry:* Точність субпіксельного ремапінгу в глобальні координати $[0, 7680] \times [0, 4320]$.
     3. *Headless Dispatcher & Memory Safety:* Ідентичність виходу NumPy `uint8` та Torch `float32`, перевірка дельта-витоків пам'яті.
     4. *PySide6 Vector Overlay:* Перевірка збереження чистого шару $Z=0$ та косметичних параметрів рамок.
     5. *Packaging Artifacts:* Валідація файлу специфікації `app.spec` та наявності всіх 4 моделей пулу.
